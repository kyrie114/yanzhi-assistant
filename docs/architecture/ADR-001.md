## 背景

需求 1.0 的约束直接规定了运行结构：

- C-01：系统分为三个进程。前端 Vue 3 和 TypeScript，由 Nginx 提供页面并把 `/api` 转发到主服务。主服务使用 Go，负责任务、切块、向量、检索、问答、图谱编排和模型调用。docreader 使用 Python，通过 gRPC 把 PDF、Office、网页、Markdown、图片和录音转成文本或页面图片；它不连接业务数据库，不生成向量，不回答问题，不抽取图谱。
- C-02：业务数据和向量放在 PostgreSQL；图谱使用 PostgreSQL 中的表，不另外部署图数据库；处理任务记在数据库中，由主服务的 worker 领取。
- C-04：交付 Web 应用和 Docker Compose 部署，不做多活集群。
- NFR-12：一条命令启动前端、主服务、docreader 和 PostgreSQL。

验收还要求：

- 检索在查询条件中限定为当前用户的资料，不能先检索再在应用层丢掉别人的切块（FR-02、AC-08-02），图谱补充也不能越界。
- 删除资料时同时去掉文件、切块、向量和只由它支撑的图谱数据（FR-03、FR-07）。
- 主服务重启后，停在解析中、向量化中或抽取中的任务标为失败，不自动重跑，也不占用 3 次手动重试（AC-03-06、AC-07-06）。
- docreader 不可用或单次调用超过 120 秒，资料失败，不生成切块（AC-03-08）。
- 更换向量模型名或维度时，未确认则配置不变；确认后旧向量退出检索，原图谱不参与补充（AC-09-05）。
- 关键词命中的专名不能因为向量分数低而被拒答（AC-06-12）。

v0.1 按旧版需求选定了 FastAPI 模块化单体，并在评审中拒绝了独立解析服务。需求 1.0 把语言、进程和通信方式写进了约束，v0.1 的决策因此不再成立，需要重新决定：主服务内部怎么组织、docreader 的边界划在哪里、任务靠什么排队、向量和图谱放在哪里。

## 决策

1. 运行时只有三类应用进程加一个数据库：Nginx（含前端构建结果）、Go 主服务、Python docreader、PostgreSQL。Compose 服务为 `web`、`server`、`docreader`、`postgres`。
2. Go 主服务是模块化单体。HTTP 接口、后台 worker 和定时器在同一个进程里；模块按 module-design.md 的依赖规则组织。主服务只有一个实例。
3. docreader 是无状态的格式转换服务，只暴露 `proto/docreader/v1/docreader.proto` 定义的 gRPC 接口，只在 Compose 内部网络监听，调用需带共享口令。它接收主服务流式发送的原件字节，返回按物理页组织的文本块、表格、抽出的图片，以及全篇没有文本时的页面图片，录音返回转写文字。它不连数据库、不挂载文件卷、不调用模型服务、不访问外网。
4. 切块、识别（调用视觉模型）、图片描述、向量化、关键词索引、预生成问法、图谱抽取全部在主服务完成。网页由主服务安全抓取后把 HTML 交给 docreader 提取正文。
5. 资料、切块、pgvector 向量、BM25 词项、图谱实体关系证据、任务表、问答和权限数据都在一个 PostgreSQL 里。任务队列就是 `jobs` 表，worker 用 `FOR UPDATE SKIP LOCKED` 认领。
6. 不部署独立的向量数据库、图数据库或消息代理。docreader 之外不再拆服务。
7. 在需求写明的 5000 切块规模内，向量检索使用带所有者、状态和代际谓词的精确近邻。HNSW 只在该预算保不住时再加，过滤谓词仍留在 SQL 中。

模块边界、端口和依赖方向见 module-design.md，gRPC 消息见 api-design.md 第 21 节。这个决策不关闭 OQ-01 至 OQ-11。

## 理由

三进程结构和语言是 C-01 规定的，本 ADR 只决定在这个框架里怎么落，使已有的一致性要求不被进程拆分打散。

docreader 的职责被约束写得很窄，正好可以做成无状态服务：给它字节，它还回页块。所有会改变业务状态的事情（状态迁移、切块、向量、图谱）都留在主服务，因此一致性仍然由一个进程、一个数据库的事务保证。docreader 不连数据库，也就不存在「两个进程各改一半状态」的情况；它崩溃或超时，只表现为一次 gRPC 调用失败，主服务按「文档解析服务暂不可用」收口。

原件由主服务流式发给 docreader，而不是让 docreader 挂载文件卷，是为了让「原始文件只能通过鉴权后的下载接口获取」只有一个实现位置，也让 docreader 不需要知道任何存储键。网页由主服务抓取，是为了把 SSRF 检查和「需要登录的地址不保存」放在一处，docreader 保持没有外网出口。

同一数据库里的事务可以同时完成三件事：资料状态变为「已完成」、切块可见、向量可查。删除也可以在一个事务里去掉切块、向量和只由该资料支撑的图谱关系，并让历史出处的外键变空。检索谓词和图谱补充的谓词直接写在 SQL 上，满足 AC-08-02。图谱规模在单用户几千个切块的量级，用实体、关系、证据三张表加索引就能在检索预算内走一跳，不需要图数据库，这也是 C-02 的要求。

任务放在 `jobs` 表并由主服务自己认领，重启回收就是启动时的一条更新：把运行中的任务和对应的对外状态改为失败，并保持手动重试计数不变。队列如果在进程崩溃后自动把消息投递回去，就会违反 AC-03-06。因此不用这种代理。

主服务单实例、worker 在进程内，使问答流式缓冲、停止标志和深度查阅的取消都能用进程内的 `context` 和 map 实现，不需要外部缓存。

5000 个 1024 维向量大约 20 MB，加上每块不超过 3 个问法的向量也在百 MB 以内。这个规模用精确近邻就能落在检索 2 秒的预算里，同时让所有者和状态过滤留在同一条 SQL 中。

## 后果

变得容易的部分：

- 越权测试可以用事务回滚的测试数据库覆盖权限、检索、图谱补充和删除。
- docreader 可以用一组样例文件单独测页码、跳页、加密和损坏，满足 NFR-09 对解析包的覆盖率要求；主服务用假 docreader 测超时和不可用。
- 更换向量代际时，用活动代际谓词让旧向量立即不可见；图谱用暂停标记退出补充。
- 新同学只需要启动四个容器。
- 关键词倒排和向量在删除切块时一起提交，避免专名索引残留。

需要接受的代价：

- 有两种语言和两套工具链。CI 要同时跑 Go 测试、golangci-lint、pytest 和 ruff，合并主分支前两侧都要通过。
- proto 是两侧共享的契约，改动要同时生成两侧代码。页码规则（物理页从 1 开始、空页不占序号）在 docreader 和主服务的测试里各钉一次。
- 50 MB 的原件要经 gRPC 再传一次。按 1 MB 分片流式发送，并调大消息上限；单机内网的开销可以接受。
- docreader 的单次 120 秒截止覆盖整份资料的解析。300 页的复杂文件若超过这个时间就会失败，需要在样例上测出 docreader 的线程数和渲染分辨率。
- 录音转写在 docreader 内完成，而需求没有规定转写引擎，也没有在 FR-08 中给出语音模型的配置项。本 ADR 按 C-01 把它放在 docreader，引擎选型列为待决事项。
- 向量维度是列类型的一部分。确认更换维度时要重建向量列，管理操作会锁表。课程数据量下可以接受。
- 单体里的模块如果互相引用，边界会消失。依赖规则写在 module-design.md，代码审查按该规则检查 import。

以后出现下列情况时再开新的 ADR，而不是在实现里悄悄拆服务：

- 单库切块规模持续超过 NFR-02，并且 HNSW 加过滤后 P95 仍超过 2 秒。
- 部署约束不再是单台机器，或需要主服务多实例。
- 识别引擎（OQ-03）或转写引擎的选型要求新增部署单元。

## 曾考虑的方案

| 方案 | 不采用的原因 |
| --- | --- |
| 保留 v0.1 的 FastAPI 模块化单体，解析留在 Python Worker | 与 C-01 的 Go 主服务、三进程结构冲突 |
| 主服务用 Go 自己解析全部格式，不要 docreader | 与 C-01 冲突；NFR-09 也单独要求 docreader 解析包的覆盖率 |
| docreader 直接读写数据库，或自己调用模型做识别和向量 | C-01 写明它不连接业务数据库、不生成向量；FR-22 写明 docreader 不调用模型 |
| docreader 挂载文件卷按路径读原件，或自己抓取网页 | 存储键和 SSRF 检查会出现在两个进程里；docreader 需要外网出口 |
| 把检索、图谱、深度查阅、通知再拆成独立服务 | 单机和一条 Compose 命令装不下这套运行单元。权限规则会复制到每个服务 |
| Milvus 或 Qdrant 存向量，PostgreSQL 只存业务 | C-02 规定向量放在 PostgreSQL。删除资料和按所有者过滤都要跨两个存储，做不到一个事务 |
| Neo4j 等图数据库存图谱 | C-02 规定图谱使用 PostgreSQL 中的表。证据要和切块同事务删除 |
| Redis 或 RabbitMQ 队列，并使用默认的失败重投 | 主服务重启后任务会再次执行。AC-03-06 要求标失败且不自动重跑；C-02 要求任务记在数据库 |
| 全局向量 Top-K 之后在应用层按用户过滤 | 与 AC-08-02 相反，也会在过滤后凑不满 Top-K |
| 主服务与 docreader 之间用 HTTP 加 JSON | C-01 规定 gRPC。流式传输大文件和页块时 gRPC 也更直接 |

这些方案在 [architecture-review.md](architecture-review.md) 里记为 Reject。

## 确认方式

实现与本决策一致，当下面几条都能在仓库里指出来：

1. Compose 文件包含 `web`、`server`、`docreader`、`postgres` 四个服务，不包含向量库、图数据库和消息代理；docreader 没有 `ports` 映射，没有挂载文件卷，没有数据库连接串。
2. `proto/docreader/v1/docreader.proto` 存在，主服务和 docreader 都从它生成代码。
3. 检索查询和图谱补充查询的 SQL 文本包含所有者、资料状态和向量代际条件。
4. 启动回收测试证明：重启后的资料状态为失败，原因是「处理中断，请重试」，`manual_retry_count` 不变；抽取中的图谱同样为失败且不计入手动重试；没有第二次模型调用。
5. 假 docreader 超时的测试证明资料失败、原因是「文档解析服务暂不可用」、切块数为 0。
6. 删除资料的测试证明切块、向量和只由该资料支撑的关系不复存在。

## 被取代的 v0.1 决策

v0.1（同日）的决策是：API 和 Worker 是同一 Python 代码库的两个进程；解析器、切块器和向量写入都在 Worker 里，不另外部署解析服务，也不使用跨进程的解析协议；解析队列就是 `documents.status`。当时的依据是旧版需求指定 FastAPI，并且没有 docreader。

v0.2 保留了其中仍然成立的部分：一个 PostgreSQL 承载业务、向量和任务状态；不用会自动重投的队列；检索过滤留在 SQL；进程内的流式缓冲；入库进度写在任务表、对外仍只有资料五态。被推翻的是语言、进程划分和「不另起解析服务」这一条，原因是需求 1.0 的 C-01 已经把它们写成约束。评审记录中对应的 R-25 已改判，见 architecture-review.md。
