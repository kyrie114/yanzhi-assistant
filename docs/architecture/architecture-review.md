## 1 这份记录记什么

架构起草时，Agent 针对进程划分、存储、检索、权限和范围提出了一批建议。本组按需求 1.0、约束 C-01 至 C-06、假设 A-01 至 A-11 给出结论。

| 结论 | 含义 |
| --- | --- |
| Accept | 写入本目录的架构包，实现时按此办理 |
| Reject | 不进入首期基线。以后若要采用，先写新的 ADR |
| 作废 | 建议所针对的功能在需求 1.0 中已经不存在，结论不再适用 |
| 改判 | v0.1 的结论与需求 1.0 冲突，按 1.0 改为相反的结论 |

本文件不补写没有发生过的对话原文，也不把 OQ-01 至 OQ-11 改成已决定。需求澄清日志第 1、2 轮确认要做邮箱验证和自助重置密码：未验证邮箱可以登录并看到提示，上传和提问返回 403；重置链接 30 分钟内有效、只用一次，成功后已签发令牌全部失效。本记录据此处理 FR-24。

v0.1 的结论是按旧版需求做出的，其后只把需求编号换成了 1.0。v0.2 在需求 1.0 上逐条重审：仍然成立的保持 Accept 或 Reject；理由或内容需要按 1.0 改写的标「v0.2 改写」；针对已删除功能的标「作废」；与 1.0 冲突的标「改判」，并由新增行承接。

统计（v0.2）：共 90 行。Accept 49 条，改判为 Accept 2 条（R-25、R-31），部分改判 2 条（R-28、R-30，各有一半接受、一半维持拒绝），Reject 32 条，作废 5 条（S-12、S-13、S-35、R-10、R-18）。编号从 S-24 和 R-25 起是后补的流水线建议，从 S-38 和 R-35 起是 v0.2 新增。

## 3 Accept 如何配合

S-01、S-02、S-03、S-04、S-19、S-38 合成 ADR-001，是首期的结构基线。其余 Accept 是这条基线上的模块规则。

权限、检索和出处是三条独立的检查，不能互相替代：

- S-05 决定能不能看见资源。
- S-07、S-19、S-39 决定候选切块从哪来；S-40 决定图谱补充能从哪来，且不越过同一范围。
- S-08 和 S-10 决定回答里留下哪些出处。S-27 把 S-08 的检查落成短别名：模型不接触切块 ID，服务端只展开本轮登记过的编号。

入库和问答的后补决定是 S-24 至 S-37。v0.2 新增的 S-38 至 S-52 把需求 1.0 新出现的能力放进同一个主服务和同一个数据库，不增加 docreader 之外的部署单元。

S-16 的配置默认值不表示 OQ-08 已关闭。若把 0.3 定义成距离，只改检索配置和 SQL 算子。

S-21 不把 FR-24 抬进必须。第一切片可以不注册邮件路由，未验证邮箱的限制同时由配置关闭；限制打开之后就必须按 api-design.md 的语义实现：未验证邮箱上传、导入、提问、深度查阅和添加订阅源时返回 403。

S-22 把 FR-01 里「注册成功后可以登录」落在登录接口上，避免注册响应和登录各发一枚令牌。

## 4 Reject 的约束

实现和后续迭代不要把第 2 节里结论为 Reject 的方案写进代码来「预留」。具体地：

- 不增加消息代理、独立向量库和图数据库；docreader 之外不再拆服务。
- 不让 docreader 连数据库、调用模型、挂载文件卷或访问外网。
- 不在应用层做跨用户的向量过滤或图谱过滤。
- 不把框架的 Agent 循环设为问答或深度查阅的入口。问答入口是固定阶段的函数列表。
- 不把资料改成默认软删除。
- 不新增清零重试次数的管理接口，除非需求先写明验收标准。
- 不自动给资料打标签。
- 不用模型的一般知识回答内容问题；寒暄分支只给简短回应。
- 不把 SSE 事件流放到进程外的缓存里。

OQ 翻转时只改 architecture.md 第 13 节指出的那个模块，并在本文件追加一行新的 Accept 或 Reject。v0.2 因需求基线整体变更做了一次统一重审，改动都在结论列标明；之后不再改写已有行的结论。

## 6 v0.2 修订说明

### 6.1 为什么重做

v0.1 按旧版需求设计，之后只把需求编号换成 1.0，设计仍是 FastAPI 单体加 Worker，并保留了导师、绑定、项目任务、提醒、Related Work 等 1.0 中不存在的功能。需求 1.0 的约束 C-01、C-02 规定了 Go 主服务、Python docreader、gRPC 和 PostgreSQL 中的图谱表，优先级也重排了（图谱和标签进入必须，阅读要点降为应该）。v0.2 按 1.0 重做全部六份文档。v0.1 中标为「新版需求无对应项」和「新版仅部分对应」的段落已全部处理：无依据的删除，部分对应的按 1.0 收窄，不再保留待确认标记。

### 6.2 删掉的设计

- 导师角色、邀请码、师生绑定与解绑、导师只读访问、导师进度看板，以及「能读不能改」的 403 规则。
- 项目、任务、完成率、导师指派任务与评论、截止提醒扫描、站内通知、提醒邮件和邮件开关。
- Related Work 草稿生成及其四步任务表、对话分叉、资料与项目的关联。
- `membership`、`workspace`、`notify`、`agents` 模块；FastAPI、Python Worker、Fernet。
- arXiv 专用检索端口（需求 1.0 只写公开网页）、`PATCH /me` 的个人开关、4 步三工具的只读循环和 MCP 专用端点。
- 团队与周期这一条驱动力（需求 1.0 没有对应约束）。

### 6.3 新增的设计

- Go 主服务（模块化单体，HTTP、worker、定时器同一进程）和 Python docreader（gRPC 契约、共享口令、内部网络）。
- 多知识库、知识库回答说明与阈值、是否启用图谱、推荐问题。
- 知识图谱：实体、关系、证据、未入库引用、抽取任务与状态、一跳补充、暂停与恢复、删除清理。
- 父子块、预生成问法、寒暄分支、FAQ 不应命中的问法。
- 深度查阅（最多 8 步，第 8 步是整理回答，此前最多 7 个动作；六类动作；停止）、可编辑并保留版本的 Wiki。
- 多种来源：pptx、xlsx、csv、epub、html、图片、录音、手工录入、文件夹相对路径；表格列说明。
- 通用任务表 `jobs`，图谱抽取的启动回收与手动重试计数。
- AES-GCM 加密模型密钥，重置密码的发信通道探测。
- 外部检索密钥、来源同步、使用偏好（只记称呼和回答语言）。
- 按 1.0 的 MoSCoW 重排的切片：必须 46 点、应该 64 点、可以 10 点。

### 6.4 仍需需求方确认的问题

下列各点需求 1.0 没有写清或彼此有出入，设计先按括号里的做法编码，并把改动点收在一个模块里：

1. 录音转写由谁完成。C-01 把录音转成文字交给 docreader，FR-22 又写明 docreader 不调用模型，FR-08 也没有语音模型的配置项。（按 docreader 内置本地转写组件设计，引擎未定，没有对应的 OQ。）
2. 标签属于知识库还是用户。FR-05 写「在自己的知识库中创建标签」，AC-06-02 中同一标签却同时含有库内的 X 和库外的 Y。（按用户级标签设计。）
3. FR-24「邮件发送失败时给出明确提示」与重置密码不暴露邮箱是否注册。（S-48：通道故障明确提示；通道正常但单封发送失败时只记日志，用户可再次申请。）
4. 回答语言。FR-06 要求语言与问题一致，AC-29-01 又要求确认后的「以后用英文回答」改变语言。（已确认的偏好优先。）
5. 实体合并的键。FR-07 写「名称相同的实体合并为一个」，没有提类型。（作者、方法、数据集、指标、研究问题按名称合并，同名不同类型时保留已有类型，随 OQ-11 一起确认。文献节点不按标题合并，合并键为 `paper:` 加资料 ID，保证每份资料有自己的文献节点。）
6. 图谱补充是否受提问范围限制。FR-07 只要求属于同一用户的已完成资料，AC-06-02 要求出处只来自所选范围。（补充限制在范围内。）
7. 更换向量模型后「资料回到待处理」是否要重新解析。（只重新向量化，以保留 FR-18 的修订文本。）
8. 知识库的删除和改名。需求只写了创建和回答设置。（本期不提供删除知识库接口。）
9. 未验证邮箱的限制属于应该级别的 FR-24，上传和提问却在必须级别的第一切片。（限制打开后，上传、导入、提问、深度查阅和添加订阅源同为 403。第一切片用配置关闭该限制，FR-24 上线时打开。）
